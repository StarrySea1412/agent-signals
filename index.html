「熟练掌握Python技术（必需），熟悉基本语法和常用库，熟悉SSE，WebSocket和Restful Api通信方法」

——顺带说一句，「Restful」是业内最常见的误写，规范写法是 RESTful。不影响它是条好要求；恰好相反，它比很多空谈「精通大模型」的 JD 诚实得多。

第一次认真读这行字，是帮朋友改简历的时候。他想投 AI 应用开发，简历上写满了自己调过哪些模型、写过多少提示词。我把这行 JD 发给他，问：SSE 是什么，答不上来；WebSocket 和 HTTP 的区别，含糊；Restful 的「资源」指什么，没概念。他问我：这些都是小东西吧，模型才是大头？

我说反了。模型是 Agent 的脑子，通信是 Agent 的嘴和耳朵。脑子再好，嘴张不开，它就只是一个孤岛上的思考者——想得再对，也拿不到天气数据、听不到用户后半句话、发不出一个字。一份「会查天气的 Agent」的实际构成是：大约一成的智能在模型调用里，剩下九成的工程在通信里——请求怎么发、流怎么接、断了怎么重连。

而这行 JD 列的三样东西，恰好是 Agent 和世界说话的全部三种方式：RESTful API 是普通话，一问一答，句句完整；SSE 是单向的广播线，服务器只管说，客户端只管听——你看到的每一个「打字机效果」，底下都是它；WebSocket 是全双工的电话，两头同时开口，谁也不用等谁。

这篇的走法很克制：全程只用一个 Agent——一个只查天气的小服务——让同一条消息在三条协议里各走一遍完整的一生。不背概念，直接看报文、看时序、看代码。三种协议不是三个知识点，是一套分工。

阅读说明：全文约九千字，七章 + 四枚小样。第 1 章拆这行 JD 的分量；第 2 章走 RESTful，附报文解剖台；第 3 章解剖 SSE 与打字机效果，附首字竞速台；第 4 章走 WebSocket，附双工对讲机；第 5 章是选型法庭，六道场景题当场判分；第 6 章把三种端点装进同一个 FastAPI 文件；第 7 章收束成可演示的三件事。四枚小样全部是确定性模型：参数可调、行为可复现，不含随机数。

一行 JD 的分量

为什么 AI 岗位不先问模型，先问通信——把第②条要求拆成三段，看每一段到底在考什么

把第②条要求横过来竖着读，其实是三句话：Python 是必需的；语法和常用库要熟；三种通信方法要懂。三句话的分量完全不同——第一句是站队，第二句是体能，第三句是真正的护城河。

第一段：为什么偏偏是 Python

不是 Python 比 Go 快，也不是它比 TypeScript 优雅。是重力。整个 AI 工具链的质量中心在 Python 上：模型侧的 transformers、vLLM，编排侧的 LangChain，还有各家模型公司的官方 SDK——Python 版几乎总是第一顺位发布、文档最全、社区最吵的那一个。你要接一个新模型，它的 README 第一行代码示例多半就是 pip install 开头。

这对 Agent 开发者意味着一件很实际的事：任何新能力，从发布到你能用，Python 的距离最短。别人还在等官方的 Rust 客户端，你已经在报 issue 了。重力不是优点，但重力决定了水往哪流。

第二段：语法和常用库，是体能不是卖点

「熟悉基本语法和常用库」听起来像客套话，其实是面试里最快的筛子。virtualenv 为什么存在、pip 和 uv 的区别、async/await 到底在等什么、pydantic 为什么成了所有 LLM SDK 的地基——这些不拉开差距，但缺一样都会当场掉队。本文第 6 章的代码会把这张清单过一遍。

第三段：通信方法，Agent 的嘴和耳朵

现在说重点。一个 Agent 的标准工作回路是：听用户说话 → 模型思考 → 决定调哪个工具 → 拿到工具结果 → 模型再思考 → 说出回答。七步里，第 3、4 步是模型发出去的 HTTP 请求，第 1、6 步是它收发文字的通道。回路七步，四步在通信。

所以这行 JD 真正在说的是：你会调模型，只是会想；你会通信，才是会说。面试官不担心你不会写 prompt——prompt 是可以背的；他担心的是你接不住流、认不出 429、分不清什么时候该用 WebSocket——这些背不会，只能见过。

RESTful API：Agent 的普通话

名词、动词和状态码——把小晴的一次工具调用放到手术台上，逐行看报文

小晴接到的第一句话是「北京今天适合跑步吗」。它自己决定要先看天气——于是它发出了这辈子第一个 HTTP 请求。这个请求长什么样，就是这一章的全部内容。

一次工具调用，就是一次 HTTP 请求

REST 的全称是 Representational State Transfer，但这个名字帮不上忙。有用的记法是把它当一门语言：所有数据都是名词（资源，写在 URL 里），所有动作都是动词（HTTP method），所有回话的语气都是状态码。GET /v1/weather?city=beijing 翻译过来就是一句话：「给我看看『北京的天气』这个资源，我只是读，不改」。

REST 的另一半性格是无状态：服务器不记得你上一句说了什么，每次请求必须自带全部信息——身份在 header 里，参数在 query 或 body 里。听起来很笨，但这是它能扛住整个互联网的原因：任何一台机器都能处理你的任何一次请求，加机器就能扩容。小晴的每次工具调用都是自足的一句话，问完就走，连接即断。

把报文解剖给你看

下面是真实的报文格式，一行不多一行不少。读报文的诀窍只有一条：每一行都有职务。第一行说「做什么」，中间的 header 说「怎么寄」，空行以下是「货」本身。

DEMO 01 / REST 报文解剖台切场景、切状态码，看整份回信怎么变
REQUESTGET /v1/weather?city=beijing
RESPONSE200 OK

读法：报文为真实格式节选（host 为示例域名）；时序数字取本地回环实测量级。试试 429——那行 Retry-After 是服务器在教你做人。

状态码是社交礼仪，不是错误提示

新手把状态码当「报错」，老手把它们当对方的语气：200 是「事情办好了」；404 是「你找的这个资源不存在，别重试了，重试也没用」；429 是「你话太密了，歇会儿再来」——而且好脾气的服务器会附一行 Retry-After: 30，明确告诉你歇多久；500 是「我这边出事了，你也别急，等会儿重试」。

这四种语气对小晴就是四种行动指令：200 走正流程，429 按秒数退避重试，500 指数退避换窗口，404 直接向模型报告「没有这个城市」。Agent 的可靠性工程，一多半是把这些语气翻译成正确行动——「见到 429 就立刻重试」的 Agent，只会被服务器拉黑得更彻底。礼貌是协议的一部分。

REST 够用了——直到用户等不及。模型生成 300 字要十几秒，普通话是一问一答，答完才能说下一句，可用户想边生成边看。这时候就需要第二条线了。

SSE：流式输出的血管

打字机效果的真相：它不是什么新技术，是一段永远不写完的 HTTP 响应

很多人猜打字机效果是 WebSocket 做的。猜错了——你在任何一家主流 AI 产品里按 F12 打开 Network 面板，找到那条回答请求，它的 Content-Type 几乎都写着 text/event-stream。SSE，Server-Sent Events。

一段永远不结束的 HTTP 响应

SSE 的原理朴素到让人失望：服务器接到请求后不关连接，把响应体当成长长的传送带，一段一段往里写。每段以 data: 开头、以一个空行结尾：

text/event-stream · 报文原文HTTP/1.1 200（Content-Type: text/event-stream）
data: {"delta": "北京今天"}
data: {"delta": "晴，18°C，"}
data: {"delta": "西北风三级。"}
data: [DONE]

就这么简单。没有新协议，没有新握手，就是一条普通的 HTTP 响应，只是永远不写句号。客户端这边，浏览器内建了 EventSource 接口，三行代码接住流；各家模型 SDK 里那个 stream=True，底下流的也是这同一种东西。

为什么是 SSE，不是 WebSocket

LLM 的输出是天然的单向流：模型往外吐字，用户不需要在这个通道里插话——话是用户先说完的。这种「服务器单方面广播」的场景，SSE 比WebSocket 合算得多：

  • 它就是 HTTP。代理、CDN、网关、负载均衡，整个互联网的基础设施不用任何改造就认得它；WebSocket 的 Upgrade 握手在很多老代理面前会被拦下来。
  • 断线重连是内建的。EventSource 断了自动重连，还带着 Last-Event-ID 头告诉服务器「我听到第几条了」，服务器从这个位置续传；每条事件还可以带 retry: 字段指定重连间隔。WebSocket 断了就是断了，心跳、重连、续传，全要自己写。
  • 代价清单极短。唯一的硬伤是方向：只能服务器→客户端。对小晴来说这不是硬伤，是刚好。

一个值得知道的坑：浏览器原生的 EventSource 只会发 GET 请求。所以当你需要 POST 一个大 prompt 去换流式响应时，SDK 们都不用它——它们拿 fetch 的 ReadableStream 手写 SSE 解析。「知道 SSE 报文格式」的实际价值就在这：绕开封装，直接读流。

首字延迟的经济学

流式真正的胜利不是「快」，是把等待变成阅读。同一份 120 token 的回答，非流式要等全部生成完才见到第一个字；流式几百毫秒就见字。人感觉第二台机器「快得多」，尽管两台机器生成完的总时间一模一样。这个差别有个行业名字：TTFT，Time To First Token，首 token 时间——它是所有对话产品的核心指标之一。

确定性模型：首 token 时间固定 250 ms，每 3 个 token 打包一个 data: 事件，事件到达按生成节拍推进。拖大 RTT 再跑一次——流式的优势会缩水但不会消失，这就是为什么 CDN 边缘节点值得做。

跑几次你会看到一个反直觉的事实：拖动「回答长度」对甲的首字伤害巨大，对乙几乎没有影响——非流式的首字时间里混进了整篇作文的工时，流式的首字时间只含网络和第一口生成。这就是为什么 2023 年之后，「API 支不支持 stream」成了对话类产品选型的第一道门槛。

但单向血管有一个天然盲区：它听不见。如果用户在小晴说话的时候想插一句「等等，还有紫外线吗」——SSE 的传送带不会为任何人回头。要会打断的对话，得换第三条线。

WebSocket：全双工的电话

一次握手借道 HTTP，之后两头随时开口——会打断的对话才像对话

SSE 是广播，HTTP 是普通话，但真人对话是两个人同时在线、谁都能随时开口。要这种效果，就需要 WebSocket：2011 年定稿的 RFC 6455，给 Web 补上的那部全双工电话。

借 HTTP 的门，进 TCP 的屋

WebSocket 的开场白是一次长得像 HTTP 的请求——但带着一句黑话：

握手报文 · GET /wsHTTP/1.1 101 Switching Protocols
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

从 101 那一行起，这条连接就不再是 HTTP 了：双方降下 HTTP 的语法，改说 WebSocket 的帧。同一条 TCP 连接上，两头都可以随时发帧、随时收帧，不必再「一问一答」。建立连接贵，但建立之后每帧的头上只有 2–10 字节——HTTP 报文光 header 就常以百字节计。这就是为什么语音、游戏、协同编辑这类高频小消息的场景，全都要它。

全双工的价值：能打断

想一个问题：你对语音助手说了半句话，突然改主意，它该不该停下来听？真人会停，半双工的系统做不到——HTTP 的世界里，回答一旦开始，你的新输入只能等下一轮请求；全双工的世界里，你的插话作为新帧当场送达，对面的生成逻辑可以立刻改道。这就是「barge-in，打断」——所有语音产品体验的分水岭。语音助手普遍选择 WebSocket（比如 OpenAI 的 Realtime API 走的就是它），不是偶然：音频帧需要高频双向流动，还要能打断。

自由的代价清单

WebSocket 给了双工自由，账单也来了：中间设施不再天然友好（老代理和某些企业网关会掐断 Upgrade 握手）；断线要自己管——协议层留了 ping/pong 控制帧用来探活，但应用层的心跳节奏、重连退避、断线期间的消息补偿，全是应用自己的事；没有 HTTP 缓存生态可借力。所以它不是「更高级」的选项，是为实时性付账的选项。需求里没有「同时、双向、高频」，就别请它出场。

三条线都见过了：普通话、广播、电话。真到设计系统的时候怎么选？下一章不开课，开庭。

高级答案：不是三选一，是三段接力

六道题做完，回头看第 1 章那张接力图，会发现小晴一次服务里三条线全用了：进来的查询和出去的工具调用是 REST，流出去的回答是 SSE，语音形态的对话是 WebSocket。真实的 Agent 系统就是这样一座三线机房——选型不是选一个协议，是给每一段交互找到它的线。面试里能把这一点说清楚的人，比背出三个定义的人值钱得多。

一个文件，三种端点

把三条信号线装进同一份 FastAPI：/v1/weather、/ask/stream、/ws，一条命令起机房

现在兑现承诺：小晴的信号机房，整个后端就是一个 Python 文件。三种协议各占一个函数，REST 三个装饰器里最不起眼，却撑着另外两个的地基。

signal_room.pyFastAPI · 完整可跑 · uvicorn signal_room:app --reload
from fastapi import FastAPI, WebSocket
from fastapi.responses import StreamingResponse
import asyncio, json, httpx

app = FastAPI()

# ── 第一棒 · REST：工具调用的入口（第 2 章）──────────
@app.get("/v1/weather")
async def weather(city: str):
    async with httpx.AsyncClient() as client:
        r = await client.get(UPSTREAM, params={"city": city})
        if r.status_code == 429:                     # 礼貌：听 Retry-After 的
            await asyncio.sleep(int(r.headers.get("Retry-After", "5")))
            r = await client.get(UPSTREAM, params={"city": city})
        r.raise_for_status()
    data = r.json()
    return {"city": city, "temp": data["temp"], "wind": data["wind"]}

# ── 第二棒 · SSE：回答流出去（第 3 章）─────────────
@app.get("/ask/stream")
async def ask_stream(q: str):
    async def gen():
        async for chunk in llm_stream(q):            # 逐 token 生成
            yield f"data: {json.dumps({'delta': chunk}, ensure_ascii=False)}\n\n"
        yield "data: [DONE]\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream")

# ── 第三棒 · WebSocket：能打断的语音对话（第 4 章）────
@app.websocket("/ws")
async def voice(sock: WebSocket):
    await sock.accept()                               # 101 握手在这里完成
    try:
        while True:
            msg = await sock.receive_text()           # 用户帧：说到一半也能来
            async for chunk in llm_stream(msg):
                await sock.send_text(chunk)           # 回答帧：边生成边发
    except Exception:
        pass                                          # 断线清理；重连是客户端的事

三个函数，三种性格

同一份代码里，三种协议的性格差一目了然：REST 端点最短，进去、拿数据、return，连接由框架收尾；SSE 端点是一个生成器——yield 一段就送一段，框架负责把每段标上 data: 和空行，media_type="text/event-stream" 就是那条传送带的出厂铭牌；WebSocket 端点是一个循环——accept() 之后连接一直活着，while True 里来一帧答一帧，是唯一需要你自己管生命周期的。

注意第 14 行那个 if r.status_code == 429：第 2 章说的「礼貌是协议的一部分」，落地就是这一行——读 Retry-After，睡够，再试。面试时聊到可靠性，能随手写出这三行的人不多。

这份文件背后的 Python 清单

JD 里「熟悉基本语法和常用库」的那张清单，其实就是这几个名字：

库在这份文件里干的活一句话记法

为什么满篇 async：对话服务的典型负载是「大量连接、各自等慢 IO」——等模型吐字、等上游 API。同步代码一个请求占一个线程，等着也是干等；异步代码等待时把服务员让出来服务别人。通信密集型服务的 Python，绕不开 async，这也是 JD 把「基本语法」和「通信方法」写在一句话里的深层原因。

从 JD 到作品

背概念没有出路，能演示才算会——三件拿得出手的事，和一条一周路径

回到开头那个改简历的朋友。他最后问：那我该背哪些八股？我说别背，面试官区分「背过」和「干过」，靠的是追问第三层——「SSE 是什么」能背；「为什么你们不用 WebSocket」开始见真章；「SSE 断线重连后从哪继续」只能干过的人才答得出。应对追问的办法只有一个：真的干一遍。

三件可以演示的事

把第 6 章那份文件跑起来之后，做这三件事，每件五分钟，做完你就超过简历上写「精通」的大多数人：

  • 演示一：现场掐流。浏览器连着 /ask/stream，在 DevTools 的 Network 面板里指出那条 event-stream 请求，把 Events 流一条条点开给人看——再顺手打开任意一家 AI 产品做同样的事。「知道打字机底下是什么」这件事本身就是筛子。
  • 演示二：亲手不礼貌。给上游接口连发请求踩出 429，先让代码无脑重试，再加 Retry-After 退避，两边各截一张图。可靠性工程的全部直觉，就在这两张图的差别里。
  • 演示三：一次打断。开两个终端连 /ws，回答生成到一半时从另一端插入新消息，展示回答当场改道。这一下胜过十页 PPT 讲「全双工」。

一周路径

如果从零开始，一周足够把这条 JD 从「认识」变成「摸过」：第 1–2 天把第 6 章的文件跑起来，故意弄坏每一行看会报什么错；第 3 天给 REST 端点补上 429 退避和超时；第 4 天用 fetch 手写一个不依赖 EventSource 的 SSE 客户端，逼自己解析一遍 data: 协议；第 5 天给 WS 端点加应用层心跳和断线重连；第 6–7 天把它部署出去，用真域名过一遍 TLS——很多 WS 问题只在线上出现。

做完这些，回头看那行 JD，它读起来会完全不同：不再是三个生词，而是三件你亲手接过的线。

模型的版本每年换三代，而这三种协议里最年轻的也已服役十五年。你花在这一章上的时间，不会随任何一次模型发布贬值。

结语：协议比模型活得久

写完这篇，那行 JD 在我眼里分了三层。表层是三个名词：SSE、WebSocket、RESTful API；中层是三种性格：普通话的规整、广播线的省心、电话的双向自由；底层是同一件事——Agent 的一切能力，最终都要经过一条线才能抵达别人。模型在数据中心里思考，而用户体验发生在协议的每一次收发之间。

这篇文章能给你的不是三条线的全部细节，而是三个带得走的判断：

RULE 01 · 单向即够，不必双工

需求是「服务器往外推」就先试 SSE：它就是 HTTP，基础设施零改造，断线续传白送。WebSocket 的自由要用心跳、重连和补偿去还贷。

RULE 02 · 状态码是对方的语气，不是错误提示

404 别重试，429 按书歇脚，500 退避再来。把状态码翻译成正确行动的那段代码，就是你系统里「可靠性」二字的实体。

RULE 03 · 选型是接力分工，不是三选一

真实系统三条线同时在岗：REST 进数据，SSE 出回答，WS 承接实时。能按交互段位分工的人，才在设计系统，而不只是在调接口。
