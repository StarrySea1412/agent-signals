WebSocket：全双工的电话

一次握手借道 HTTP，之后两头随时开口——会打断的对话才像对话

SSE 是广播，HTTP 是普通话，但真人对话是两个人同时在线、谁都能随时开口。要这种效果，就需要 WebSocket：2011 年定稿的 RFC 6455，给 Web 补上的那部全双工电话。

借 HTTP 的门，进 TCP 的屋

WebSocket 的开场白是一次长得像 HTTP 的请求——但带着一句黑话：

握手报文 · GET /wsHTTP/1.1 101 Switching Protocols
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

从 101 那一行起，这条连接就不再是 HTTP 了：双方降下 HTTP 的语法，改说 WebSocket 的帧。同一条 TCP 连接上，两头都可以随时发帧、随时收帧，不必再「一问一答」。建立连接贵，但建立之后每帧的头上只有 2–10 字节——HTTP 报文光 header 就常以百字节计。这就是为什么语音、游戏、协同编辑这类高频小消息的场景，全都要它。

全双工的价值：能打断

想一个问题：你对语音助手说了半句话，突然改主意，它该不该停下来听？真人会停，半双工的系统做不到——HTTP 的世界里，回答一旦开始，你的新输入只能等下一轮请求；全双工的世界里，你的插话作为新帧当场送达，对面的生成逻辑可以立刻改道。这就是「barge-in，打断」——所有语音产品体验的分水岭。语音助手普遍选择 WebSocket（比如 OpenAI 的 Realtime API 走的就是它），不是偶然：音频帧需要高频双向流动，还要能打断。

自由的代价清单

WebSocket 给了双工自由，账单也来了：中间设施不再天然友好（老代理和某些企业网关会掐断 Upgrade 握手）；断线要自己管——协议层留了 ping/pong 控制帧用来探活，但应用层的心跳节奏、重连退避、断线期间的消息补偿，全是应用自己的事；没有 HTTP 缓存生态可借力。所以它不是「更高级」的选项，是为实时性付账的选项。需求里没有「同时、双向、高频」，就别请它出场。
