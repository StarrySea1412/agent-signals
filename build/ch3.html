SSE：流式输出的血管

打字机效果的真相：它不是什么新技术，是一段永远不写完的 HTTP 响应

很多人猜打字机效果是 WebSocket 做的。猜错了——你在任何一家主流 AI 产品里按 F12 打开 Network 面板，找到那条回答请求，它的 Content-Type 几乎都写着 text/event-stream。SSE，Server-Sent Events。

一段永远不结束的 HTTP 响应

SSE 的原理朴素到让人失望：服务器接到请求后不关连接，把响应体当成长长的传送带，一段一段往里写。每段以 data: 开头、以一个空行结尾：

text/event-stream · 报文原文HTTP/1.1 200（Content-Type: text/event-stream）
data: {"delta": "北京今天"}
data: {"delta": "晴，18°C，"}
data: {"delta": "西北风三级。"}
data: [DONE]

就这么简单。没有新协议，没有新握手，就是一条普通的 HTTP 响应，只是永远不写句号。客户端这边，浏览器内建了 EventSource 接口，三行代码接住流；各家模型 SDK 里那个 stream=True，底下流的也是这同一种东西。

为什么是 SSE，不是 WebSocket

LLM 的输出是天然的单向流：模型往外吐字，用户不需要在这个通道里插话——话是用户先说完的。这种「服务器单方面广播」的场景，SSE 比WebSocket 合算得多：

  • 它就是 HTTP。代理、CDN、网关、负载均衡，整个互联网的基础设施不用任何改造就认得它；WebSocket 的 Upgrade 握手在很多老代理面前会被拦下来。
  • 断线重连是内建的。EventSource 断了自动重连，还带着 Last-Event-ID 头告诉服务器「我听到第几条了」，服务器从这个位置续传；每条事件还可以带 retry: 字段指定重连间隔。WebSocket 断了就是断了，心跳、重连、续传，全要自己写。
  • 代价清单极短。唯一的硬伤是方向：只能服务器→客户端。对小晴来说这不是硬伤，是刚好。

一个值得知道的坑：浏览器原生的 EventSource 只会发 GET 请求。所以当你需要 POST 一个大 prompt 去换流式响应时，SDK 们都不用它——它们拿 fetch 的 ReadableStream 手写 SSE 解析。「知道 SSE 报文格式」的实际价值就在这：绕开封装，直接读流。

首字延迟的经济学

流式真正的胜利不是「快」，是把等待变成阅读。同一份 120 token 的回答，非流式要等全部生成完才见到第一个字；流式几百毫秒就见字。人感觉第二台机器「快得多」，尽管两台机器生成完的总时间一模一样。这个差别有个行业名字：TTFT，Time To First Token，首 token 时间——它是所有对话产品的核心指标之一。

确定性模型：首 token 时间固定 250 ms，每 3 个 token 打包一个 data: 事件，事件到达按生成节拍推进。拖大 RTT 再跑一次——流式的优势会缩水但不会消失，这就是为什么 CDN 边缘节点值得做。

跑几次你会看到一个反直觉的事实：拖动「回答长度」对甲的首字伤害巨大，对乙几乎没有影响——非流式的首字时间里混进了整篇作文的工时，流式的首字时间只含网络和第一口生成。这就是为什么 2023 年之后，「API 支不支持 stream」成了对话类产品选型的第一道门槛。

但单向血管有一个天然盲区：它听不见。如果用户在小晴说话的时候想插一句「等等，还有紫外线吗」——SSE 的传送带不会为任何人回头。要会打断的对话，得换第三条线。
