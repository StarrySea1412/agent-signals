Agent 的智能住在模型里，能力住在通信里。这张图把一次服务的通信全景拆成三段：上半部是三条线各自的户口，中部是它们在真实服务里的接力分工，底部是公共的协议与 Python 底座。选型不是三选一，是给每段交互找到它的线。

SECTION A · 三条线的户口 — 每条线六个维度

RESTful APIHTTP/1.1 · RFC 9110 · 1991–
  • 方向一问一答，答完即断
  • 语法名词（URI）＋动词（method）
  • 语气状态码：200 / 404 / 429 / 500
  • 恢复重发即可，无状态可任意扩容
  • 开销整份报文，header 以百字节计
  • 场景工具调用、查询、表单
SSEtext/event-stream · WHATWG HTML
  • 方向服务器 → 客户端，单向流
  • 形态一段永远不写完的 HTTP 响应
  • 格式data: 行 ＋ 空行，事件逐包推送
  • 恢复内建：自动重连 + Last-Event-ID 续传
  • 开销每事件一行 data + 空行
  • 场景流式回答（TTFT）、进度推送
WebSocketRFC 6455 · 2011–
  • 方向双向同时，随时开口
  • 形态借 HTTP 握手（101），改说帧协议
  • 会话一次握手，长期活着
  • 恢复自管：心跳、重连、断线补偿
  • 开销帧头仅 2–10 字节
  • 场景语音（可打断）、协同、实时游戏

SECTION B · 一次服务的接力 — 同一段回答，三种协议各跑一棒

第一棒 · REST

模型决定调工具：向天气服务发一次标准请求，拿回温度风力，连接即断。429 时按 Retry-After 歇脚。

模型开始回答：不憋整段，一个词一个词往流里写。用户几百毫秒见首字，等待变成阅读。

GET /ask/stream → event-stream
→
第三棒 · WS

换语音形态：音频帧高频双向流动，用户说到一半能打断，回答当场改道。
